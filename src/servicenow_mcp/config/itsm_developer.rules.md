ITSM work (Incident, Problem, Change, Request) on OOTB tables. Start from a record number: get_record_context(number) returns its links (incident.rfc / caused_by / problem_id / parent_incident, problem.rfc, change parent, REQ→RITM→SCTASK, task.universal_request, task_rel_task), approvals with delegates, RITM variables with labels, child tasks, SLAs and flow runs in one call — do not rebuild that from sn_query. "What runs when this table changes" is get_table_automation(table, operation): business rules in execution order with their conditions, flow triggers, workflows, client scripts, UI/data policies, notifications, SLA definitions, assignment and approval rules, each marked OOTB or customer. A catalog item's whole definition (variable sets, choices, catalog UI policies, client scripts, flow/workflow) is manage_catalog get_item detail=full. Flow logic is reviewed with manage_flow_designer get_detail include_structure=true; act on its warnings. Flows are read-only here: change them in Flow Designer and ship them with export_record_xml. States are codes: task 1 Open, 2 Work in Progress, -5 Pending, 3 Closed Complete, 4 Closed Incomplete, 7 Closed Skipped; problem 101 New … 106 Resolved, 107 Closed; approvals requested/approved/rejected. A state write is proven only by the re-read the tools return: applied:false means a business rule or state model refused it, so use the form's UI action instead of retrying. Approve or reject through manage_approval; acting for someone else needs confirm_on_behalf=<their user_name>. Order test requests with manage_request_item action=order (variables are checked against the item first). Config writes: dry_run first, check manage_session_context for the right update set before every write, never write into an OOTB record (copy it). On a failed or empty read, act on `availability`: not_installed, forbidden, absent, undetermined — none of them means zero.

Design: change the least custom layer that does the job, in this order — (1) theme SCSS variables, (2) the theme's CSS includes, (3) page layout classes, page and widget-instance CSS/options, (4) a COPY of a header/footer or widget. Never edit an OOTB theme, widget or header/footer record. Rungs 1-2 are here: get_portal(portal_id) shows a portal's whole theme (its SCSS variables, the portal's own css_variables, header/footer, CSS/JS includes, matching Next Experience theme); download_server_sources(scope, families=[theme]) writes sp_theme/<name>/css_variables.scss, sp_portal/<suffix>/css_variables.scss, sp_css/<name>/css.scss, header/footer files and Next Experience sys_ux_theme/<name>/theme.json and sys_ux_style/<name>/style.json; edit, diff_local_component, update_remote_from_local (JSON that does not parse is refused). A theme's variables reach every portal using it; a portal's css_variables reach that portal only. Next Experience: a workspace's theme is m2m_app_config_theme (ux_app_configuration → theme); a theme's tokens are the sys_ux_style rows linked by m2m_theme_style (order) — read both with sn_query, never pull style bodies into context (they run to 150KB; download them). To copy an OOTB theme, use the platform form (Insert and Stay) and point the portal at the copy there. Rungs 3-4 need the portal_design add-on (MCP_TOOL_PACKAGE=itsm_developer,portal_design) — say so instead of working around it.

Record writes take numbers for links. Incident: caused_by = the change that caused it (stored on the incident; change_request has no caused_by), rfc = the change that fixes it, problem_id, parent_incident; states 1 New, 2 In Progress, 3 On Hold, 6 Resolved, 7 Closed, 8 Canceled, and On Hold needs hold_reason (1 Awaiting Caller, 3 Awaiting Problem, 4 Awaiting Vendor, 5 Awaiting Change). Problem tasks (PTASK): manage_problem add_task. Standard change: manage_change list_templates, then create_standard template_id (created through the documented Change REST API and re-read). A change raised from a request: create with parent=<RITM or SCTASK>. Change models and approval policies are listed by get_table_automation(change_request); which policy a change gets is decided at runtime, so applies_to stays not_verified — do not guess it. get_record_context approvals carries SELF_APPROVAL when an approver is the record's assigned_to (or a change's requested_by): report it, never approve over it. A record producer is manage_catalog create_record_producer (created inactive, target table checked); ordering one with manage_request_item order returns the record it created. Item options (hide quantity, add to cart, attachment, delivery time; request_method order/request/submit; hide_sp) are update_item item_options by sc_cat_item column — the form's Portal Settings tab uses the *_v2 columns — and update_item also links an existing item to a flow; applied:false means the instance did not keep it. A two-column form section is create_variable Container Start (layout 2across or 2down) … Container Split … Container End, ordered around the variables it holds. Who can see an item: create_user_criteria from user/group/role/company/department/location sys_ids (scripted criteria are not written here), then attach_user_criteria access=available|not_available on the item or its category; get_item detail=full lists both lists, and a record producer's after_submit names the target-table automation to read. Assignment and approval rules: manage_task_rule kind=assignment|approval; rule scripts are not written here and OOTB rules are read-only. REQ-level approvals come from the approval rules on sc_request. Choice lists: manage_choice list shows rows_from, the table that owns the list; set/deactivate write there, a list owned by a parent table needs confirm_inherited=<owner>, and options are deactivated, never deleted. Major Incident Management and Universal Request may not be installed: availability not_installed means build nothing on them.
